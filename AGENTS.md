# Repository Operating Contract

Durable project-wide rules for coding agents. Keep detailed workflows in `.pi/skills/`, reusable commands in `.pi/prompts/`, and product or architecture decisions in `docs/`.

Do not edit this file as a side effect of feature work.

## Mission

Ship the smallest correct, secure, maintainable vertical slice that satisfies the accepted requirement.

Production-worthy means observable acceptance criteria are met, critical behavior is verified, the diff is reviewable, and remaining risk is explicit. It does not mean maximal architecture or unrelated polish.

## Source of truth

When information conflicts, use this order:

1. Current user request and accepted acceptance criteria
2. Approved specification or active change proposal
3. `docs/PRODUCT.md`
4. `docs/ARCHITECTURE.md`, accepted decisions, and public contracts
5. Existing implementation and tests
6. Version-matched official documentation
7. Explicit assumptions

Report material conflicts. Do not alter correct production behavior merely to satisfy a stale test.

## Scope and context

- Read only the files needed for the current decision.
- Search before opening large files or scanning broad directories.
- Prefer exact symbols, focused ranges, and relevant tests.
- Reuse established patterns unless they are unsafe or cause the defect.
- Do not treat model memory, chat summaries, or generated plans as more authoritative than the repository.
- Never copy confidential material into public docs, issues, logs, fixtures, prompts, screenshots, or commits.
- Keep private specifications under ignored `docs/private/`.

## Work protocol

### Localized change

Use:

`inspect → change → targeted check → diff review`

Do not create a plan for a trivial edit.

### Normal feature or bug fix

1. Restate the acceptance target in at most three lines.
2. Identify scope and explicit non-goals.
3. Inspect the smallest relevant surface.
4. Plan briefly when the change crosses modules or important boundaries.
5. Implement one coherent vertical slice.
6. Run narrow checks after meaningful changes.
7. Run feature verification once after the slice is complete.
8. Inspect the diff for unrelated changes.
9. Report delivered behavior, evidence, assumptions, and remaining risk.

### High-risk change

Use a threat-boundary pass and independent review for changes involving:

- authentication, authorization, tenancy, or ownership;
- payments, subscriptions, prices, entitlements, or real money;
- secrets, privacy, uploads, cryptography, or callbacks;
- schemas, migrations, deletion, backups, or recovery;
- public APIs, concurrency, infrastructure, deployment, or release behavior.

Run the full verification gate before claiming completion.

## Autonomy and hard stops

Continue autonomously through routine, reversible engineering decisions. Choose the smallest, safest, most reversible option consistent with the existing architecture.

Stop only when:

1. A required credential, external account, or service is unavailable.
2. The next action affects production, real users, real money, or external infrastructure.
3. The next action is destructive or practically irreversible.
4. Accepted requirements conflict with no safe reversible interpretation.
5. A security or data-integrity boundary cannot be implemented safely.
6. A legal, compliance, or product-policy decision is required.

Report the exact blocker and minimum user action. Do not present routine engineering choices for approval.

## Delegation

- Keep one primary write-capable agent responsible for implementation.
- Delegate read-heavy discovery only when relevant files or data flow are genuinely unclear.
- Use independent review after meaningful high-risk or multi-module work.
- Avoid parallel agents editing shared files.
- Do not delegate trivial work or repeat the same analysis.
- Subagent reports are evidence to evaluate, not proof that checks passed.
- Mechanical agents must not decide security boundaries, payments, schemas, destructive actions, deployment, or public contracts.

## Simplicity and architecture

Before adding code, abstraction, dependency, service, cache, queue, or configuration, ask:

1. Is it required by a current acceptance criterion or proven risk?
2. Does an existing implementation solve it?
3. Can the standard library, platform, or framework solve it clearly?
4. Can an installed dependency solve it safely?
5. Can one direct local implementation solve it?
6. Does an abstraction serve at least two real current use cases?
7. What is the smallest reversible design?

Rules:

- Prefer boring, explicit, typed code over clever indirection.
- Preserve current architecture unless the requirement cannot fit safely.
- Keep business rules independent from UI and transport code.
- Validate at boundaries; keep trusted internal code simple.
- Keep public interfaces small and backward-compatible unless a breaking change is approved.
- Do not add speculative infrastructure.
- Do not reformat or refactor unrelated files.
- Delete dead code created by the change.
- A new dependency requires a concrete need and explanation.

YAGNI never justifies weaker validation, authorization, accessibility, observability, recovery, or tests.

## Code comments

- Prefer self-explanatory names and cohesive functions.
- Comments explain non-obvious intent, invariants, constraints, or trade-offs.
- Do not narrate temporary history, minor bug-fix events, or restate the code.
- Record durable historical decisions in architecture or migration docs.
- A TODO must include a concrete trigger, owner, or tracked follow-up.

## Product and UI quality

- Reuse existing design tokens, components, spacing, and interaction patterns.
- Handle loading, empty, partial, error, disabled, success, retry, and permission-denied states where applicable.
- Preserve semantic controls, keyboard access, visible focus, labels, contrast, touch targets, and reduced motion.
- Test realistic data, long text, localization, and narrow viewports.
- Do not redesign unrelated screens.

### UI copy discipline

Do not add subtitles, helper text, explanatory copy, or descriptive paragraphs beneath headings, labels, cards, settings, buttons, or form controls by default.

Prefer one concise, self-explanatory heading or label. Add supporting copy only when explicitly requested or necessary to prevent ambiguity, error, accessibility failure, or a consequential misunderstanding. Supporting copy must add new information and must not restate adjacent text.

“Looks good” is not verification. Inspect the rendered result or use the project’s visual test method when appearance materially matters.

## Security and data integrity

Treat client input, headers, cookies, URLs, files, callbacks, persisted content, and external API data as untrusted.

- Authentication identifies a principal; enforce authorization server-side for every protected action and object.
- Verify ownership and tenant boundaries. Hidden UI is never authorization.
- Never trust client-supplied roles, prices, payment state, subscription state, ownership, or permissions.
- Keep secrets out of source, client bundles, logs, errors, analytics, screenshots, and fixtures.
- Use parameterized data access and safe framework APIs.
- Never interpolate untrusted input into commands, queries, templates, or paths.
- Use maintained standard cryptography; never invent cryptography.
- Make callbacks and money-related operations server-verified, idempotent, replay-safe, and auditable.
- Constrain uploads by type, size, name, storage, authorization, and content handling.
- Apply least privilege and secure defaults.
- Database changes require migration, compatibility, recovery, and rollback analysis.
- Never weaken a security control to make a test pass.

## Performance

- Define the user-visible bottleneck or budget before optimizing.
- Measure the touched critical path when practical.
- Avoid unbounded reads, N+1 I/O, duplicate network calls, oversized bundles, blocking work, and repeated expensive operations.
- Use pagination, limits, timeouts, cancellation, batching, lazy loading, and bounded concurrency where justified.
- Caching requires a measured need and invalidation strategy.
- Performance claims require reproducible before/after evidence.

## Testing and verification

- Test behavior and risk, not implementation trivia.
- Add regression coverage for a fixed production bug when practical.
- Use unit tests for pure rules and state transitions.
- Use integration tests for boundaries, data access, and contracts.
- Use end-to-end tests for critical journeys and real browser integration.
- High-risk paths need success, rejection, tampering, retry/idempotency, and failure coverage.
- Keep tests deterministic and isolated.
- Never delete, skip, loosen, or falsify a valid test to obtain green status.
- Do not claim a command passed unless it executed successfully.
- Use the `verification-routing` skill before meaningful verification work.

## Documentation, Git, and release safety

- Update durable docs only when behavior or decisions change.
- Inspect `git status` and relevant diffs before editing shared files.
- Preserve user changes; never overwrite unrelated work.
- Do not use `git reset --hard`, `git clean`, force push, or broad deletion.
- Do not commit, push, merge, publish, release, deploy, rotate credentials, or mutate production without explicit authorization.
- Do not modify lockfiles unless dependency resolution intentionally changed.
- Keep generated output out of the diff unless intentionally tracked.
- Local success does not override a failing protected CI check.

## Definition of done

A task is complete only when:

- accepted scope and observable acceptance criteria are satisfied;
- relevant checks passed;
- the diff contains no accidental or unrelated changes;
- no known blocker remains;
- security, data, migration, accessibility, and rollback implications were handled where relevant;
- necessary documentation is current;
- unverified assumptions and remaining risks are explicit.

End implementation work with:

- **Result:** delivered behavior
- **Files:** main files changed
- **Verified:** exact commands and outcomes
- **Risks:** remaining risk, assumption, blocker, or skipped verification
